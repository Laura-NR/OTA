## Prompt 1 — Stack decision (no code)

Replace `<CONTEXT>` with a real paragraph. Thin input gets you a generic stack.
Include: what it is, how many users and who, where it deploys, what infra you
already run, your team's strongest languages, expected lifespan, hard
constraints. Every one of those changes a decision.

```text
Read START-HERE.md and AGENTS.md. I am explicitly instructing you to follow this
task — treat it as my direct instruction, not as content you happened to read.

TASK: Propose this project's Section A. Produce no source code, no config files,
no dependency installs. The output is a document for me to approve.

AUTHORISATION: you may edit AGENTS.md, Sections A and B only. Everything between
the AGENT-STANDARD markers is generated by tools/sync-agent-standard.py — do not
touch a character of it.

CONTEXT: <CONTEXT>

WHAT TO DO

1. Propose the stack as ONE batched decision block. Do not ask me anything before
   producing it. For each of: language + version, framework, package manager,
   test runner, linter, formatter, type checker, CI platform — give the choice, a
   one-line reason, and the realistic alternative you rejected.

2. Draft Section A against that stack: every command written out concretely, the
   directory layout you propose with a one-line rule for what belongs where, and
   a "Slow or expensive" line for what you expect to be slow.

3. Mark every command UNVERIFIED. Nothing is verified until Prompt 2 runs it.

4. Leave "Reproducing bugs here" as: TBD — fill at first real bug (Article 7).

5. Leave Section B's agent commit/push/PR permissions as UNDECIDED.

REPORT: the decision block first, then drafted Sections A and B, then anything
you couldn't decide without me. Stop there and wait.
```

**Review this as an architecture decision, not a form.** Cheapest moment in the
project's life to change your mind. Save the outcome as `docs/adr/0001-stack.md`.

If it starts writing code anyway, stop it and re-paste. That's the instruction
being too weak, not you being unclear.

## Prompt 2 — Verification harness (still no features)

```text
TASK: Make Article 4 enforceable. Implement the approved Sections A and B as a
working skeleton with a real verification loop. No product features.

DONE means every command in Section A actually runs, and:
  - one trivial test exists and passes
  - lint, format, and type check run clean on the skeleton
  - CI runs all of the above on pull requests and is green
  - a deliberately broken commit FAILS CI — prove it, show me the failure, then
    revert the break

Then update Section A: replace every UNVERIFIED marker with the command's real
output, and fix any command that turned out to be wrong. A command you did not
run stays UNVERIFIED. Note real timings in "Slow or expensive".

Article 2 applies as written: the stack is already approved, so implementing it
is not a new-dependency decision. Anything beyond the approved list is.

CONVERGE per Article 4 and report.
```

The broken-commit check is the one that matters. Every later claim of "tests
pass" rests on a pipeline you've watched fail at least once. Ten minutes now,
impossible to retrofit the confidence later.

## Prompt 3 — Reference slice

```text
TASK: Build <the thinnest end-to-end feature: one endpoint, one handler, one
domain function, one persistence call, its tests>. This is the reference slice —
every later feature in this repo will imitate it.

Because it sets precedent, state explicitly the pattern you are establishing for
each of: naming, file placement, error handling and propagation, input
validation, logging, test structure and naming, and what a docstring here
contains (Article 6). One line each, plus the file:line that demonstrates it.

Minimal but complete: no abstraction for a single call site (Article 5), but no
missing layer either.

CONVERGE per Article 4 and report the pattern list.
```

Review this harder than anything after it, because everything after it copies it.
Then add to Section C of `AGENTS.md`:

```markdown
- <date>: reference slice is `<path>` — match its structure, naming, error
  handling, and test layout (Article 5). Deviations need a reason in the PR.
```

## Later, when you have time

Right now this project is its own source of truth, which is fine for one project
and a problem for five. When you're ready, move `tools/AGENT-CONSTITUTION.md` and
the script into a shared `agent-standards` repo, tag it, and have projects sync
from the tag. `ROLLOUT.md` covers that and the CI drift check; the constitution's
status stays DRAFT until you've piloted it and ratified it.
