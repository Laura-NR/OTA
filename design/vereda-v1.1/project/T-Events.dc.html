Every component, its event, its payload

Doc 13 asks for an event taxonomy before pixel work. This sheet is that taxonomy for the screens on this canvas: the seven funnel stages mapped to artboards, the parameters that ride on every event, one row per instrumented component, and the empty and error states that must be measured because that is where people leave. Names are snake_case, one event per user intention, fired on commit (click, submit, change), never on hover or keystroke.

01 · Funnel stages → screens

Doc 13's seven stages, renamed for a product where nothing is charged until the hosts confirm. Each screen knows its stage; the stage is a parameter on every event it emits.

02 · Parameters on every event

Added by the shell, never by the component. Identity is a salted hash; no names, emails, passport numbers or free text ever enter an event (spec §8.2, doc 12).

{
  "event":        "package_viewed",
  "ts":           "2026-10-10T13:42:07Z",     // origin time; worker app: queued offline
  "session_id":   "s_…",  "user_id": "h_…",   // user_id only when signed in, hashed
  "app":          "web | mobile_web | worker | ops_lite | admin",
  "screen":       "Package",                   // artboard name = screen id
  "funnel_stage": 3,
  "locale":       "en | es | fr",  "currency": "EUR",
  "market":       "DE",                        // country of the visitor, not nationality
  "device_type":  "desktop | tablet | phone",
  "viewport":     "xs | sm | md | lg | xl",   // DS sheet 07 breakpoints
  "network":      "4g | 3g | 2g | offline | unknown",
  "consent":      "essential | analytics | marketing",
  "ab_variant":   null,
  "role":         null                          // admin apps: super_admin | ops_admin | support | worker
}

03 · How a component declares its event

The attribute pattern already used on DS sheet 06. The shell reads the attributes on commit and adds the common parameters; developers never hand-write a tracking call inside a component.

<button class="btn btn-p"
  data-analytics-event="cta_click"
  data-analytics-cta="request_proposal"
  data-analytics-step="5">Request proposal</button>

<a href="/packages/eco-vinales"
  data-analytics-event="search_result_clicked"
  data-analytics-package="PKG-ECO-VIN"
  data-analytics-position="2">…</a>
  • Analytics events fire only after the analytics cookie is accepted (DS sheet 04 consent). Essential events (api_error, payment_*, booking_*) are logged first-party regardless, without the session id.
  • page_view once per screen render; tab and step changes are their own events, not new page views.
  • Worker app and Ops Lite queue events with the sync queue (G-Sync) and keep the origin timestamp.

Naming and ownership rules

  • object_verb_past: package_viewed, offer_declined. No screen names in event names; the screen is a parameter.
  • A new component gets its event in this table before it is built; the row is the ticket's acceptance criterion.
  • Identifiers in payloads are ids (package_id, booking_code), never titles, never free text typed by a person.
  • Retention of raw events follows the traveler retention clock (6 months after the last COMPLETED trip, then anonymised; spec §3.5).
  • Owner: product analytics, reviewed with the quarterly KPI review (doc 13 §6). The stack is doc 13 §5: GA4 + BigQuery + Metabase at minimum.
